## 线上事故：分析报 `access token 无效`（已修）

- 现象：`{"code":"AUTH_UNAUTHORIZED","message":"无权进行此操作，access token 无效","success":false}`。
- 根因：`analyzeVideoGrid` 把 **中转 key（渠道里的 `sk-...`）** 放进了 `Authorization`，
  而 `/api/user/copy/analyze` 挂在 `selfRoute` 的 `middleware.UserAuth()` 上，
  只认后台登录态 token（`service.ParseDashboardAccessToken` 或 PAT）。
  中转 key 既不是登录态 token 也不是 PAT → `service.ErrAuthTokenInvalid`
  → `middleware/auth.go` 的 `writeDashboardAuthError` 返回 `AUTH_UNAUTHORIZED` + 该文案。
- 修法：`Authorization: Bearer <session.token>`；中转 key 仍走 body 的 `apiKey`，由服务端
  `callChatCompletion` 代发 `/v1/chat/completions`。函数签名加 `sessionToken` 参数，
  页面从 `useUserStore.getState().session.token` 取，空值直接提示「请先登录」而不是抽完帧才报错。
- 顺带：提交/轮询错误改用 `readAxiosError`，把后端中文 message 透出来（不再只有 `Request failed with status code 401`）。
- 教训：**画柚里凡是打到 `/api/user/**` 的请求都必须用 `session.token`；`channel.apiKey` 只能用于 `/v1/**` 中转。**
- 发布到 `releases/web/20261119-101912`（bundle `index-BBjOgehR.js`），上一版 `20261119-101803`。- 服务端自调 `/v1/chat/completions` 走 nginx `location /v1/`（`proxy_read_timeout 300s`、
  `client_max_body_size 60m`），`block_scraper` 只作用在 `location /assets/`，Go 默认 UA 不会被 403。



## 安全修复：分析接口不再收 key / baseUrl（SSRF + 凭证入体）

- 审计结论：
  - 原 `copyAnalyzeRequest` 带 `apiKey`（用户中转 key）和 `baseUrl`，服务端直接
    `POST <baseUrl>/v1/chat/completions` → 任意登录用户可把 baseUrl 指向内网（SSRF），
    同时凭证进了请求体（DevTools/抓包/异常上报都能留）。
  - ASR 干净：腾讯云密钥只在 env，不入库不下发；job 只存 status/content/error。
  - 既有问题（未改）：Gemini 视频轮询把 key 拼在 URL query（`video.ts:334`、
    `model-plugin.ts:700`），是 Google Files API 的用法，key 发往 Google 不经过我们 nginx。
- 修法：
  - 请求体只剩 `{model, prompt, image}`；后端 `pickUserRelayKey(userId)` 从 `tokens` 表取启用令牌，
    `relayLoopbackURL()` 固定 `http://127.0.0.1:$PORT`（PORT env，缺省 `*common.Port`=3000）。
  - 前端 `analyzeVideoGrid` 用同源相对路径 `/api/user/copy/analyze` + `Bearer session.token`。
  - userId 缺失 401；无可用令牌返回「当前账号没有可用的 API 令牌」。
- 发布：后端 `new-api:0a6cfcb1c`（**必须先发后端**，新前端配旧后端会 Bearer 空值）；
  画柚 `releases/web/20261119-102629`，bundle `index-DqBW0te4.js`。
- 校验：`grep -a` 容器内 `/new-api` 二进制能找到「当前账号没有可用的 API 令牌」；
  前端 bundle 里端点是字面量 `"/api/user/copy/analyze"`，Authorization 用 session token。

## 登录 429 事故：续期风暴打满敏感操作桶

- 现象：`/profile` 3 秒 110 个请求（36 self / 35 log/self / 21 refresh / 18 catalog），
  第 21 次 refresh 触发 `AUTH` 之外的另一层限流 → 同 IP 的 `POST /api/user/login` 一起 429，
  用户被锁登录页 20 分钟（12:41:51 → 13:01:51），期间点了 12 次登录全 429。
- 根因：
  1. 网关 `CriticalRateLimit` = **20 次 / 20 分钟 / IP**，key 是 `"CT" + ClientIP`，
     `/api/user/auth/refresh` 与 `/api/user/login` **共用同一个桶**。
  2. 前端续期后 `setSession({token})` 换新 token，而 AuthGuard / ModelPicker /
     profile / UsageLedger 的 effect 都依赖 `session.token` → 续期一次，四处重拉。
- 修法：
  - 后端新增 `RefreshRateLimit()`（mark `"RF"`，120 次/5 分钟，env `REFRESH_RATE_LIMIT*`），
    `auth/refresh` 改用它；login 仍走 CT。提交 `f1600b6b3`。
  - 前端 `session.ts`：两次续期硬下限 10s（`MIN_REFRESH_INTERVAL_MS`）+ 429 退避 30s
    （`refreshBlockedUntil`）+ 429 不清会话。
  - `http.ts` 401 重试时若续期拿不到 token，不再立刻 `clearSession`（真失效由 session.ts
    在 4xx 清；限流/网络问题不该把人踢去登录页）。
  - 四个 effect 的依赖从 `session.token` 改成「有没有登录」，token 用
    `useUserStore.getState()` 现取。提交 `3f25633`。
- 发布：后端 `f1600b6b3`；画柚 `releases/web/20261119-131241`（`index-DFTkBN1B.js`）。

## 视频选了 16:9 却出竖屏（2026-11-20 上午）

- 实证：2026-11-20 09:08:41 的 text_to_video（`vw_b05fc3c4@308`，tasks.id=216）
  上游 `data.aspectRatio = "9:16"`，但界面选的是 16:9 —— 说明**发出去的就不是 16:9**。
- 根因：`web/src/services/api/video.ts` 的 `mapVideoSize()` 三个分支全返回竖屏
  （480x854 / 720x1280 / 1080x1920），与入参比例无关。1280x720 → 720x1280，
  网关插件 `ratioFromSize()` 反推出 9:16 传给上游。
- 修法：按短边选 480/720/1080 档位，长边按原比例算，横竖保持原方向；`auto` 不再兜底塞尺寸。
- 影响面：openai 视频路径全模型，以及 /copy 的统一参数面板（它传 ratio → computeVideoSize → 同样过 mapVideoSize）。
- 提交 `15c324b`，发布 `index-DJFZLhIz.js`。

## /copy 分析报 JSON 解析错（2026-11-20）

- 现象：`Expected ',' or ']' after array element in JSON at position 18056 (line 765 column 6)`。
- 原因：分析结果约 18KB（~765 行，≈6k token），后端 `max_tokens` 只给 4000 → 输出被截断 →
  模型吐半截 JSON → `extractJson` 里裸 `JSON.parse` 抛原始 SyntaxError，原样显示给用户。
- 修法两条：
  1. 后端 `controller/copy_asr.go`：`max_tokens` 4000 → 8000（提交 `8ca71914a`）。
  2. 前端 `copy-video.ts`：`extractJson` 先 `parseJsonLoose`（含「截掉 JSON 后面的说明文字」），
     失败再 `closeUnclosedJson`——字符串感知地找最后一个结构闭合点并补括号，保住已完成部分；
     都失败才给中文提示「模型返回的 JSON 不完整（多半是分镜太多被截断）…」（提交 `19b182f`）。
- 关键实现细节：不能用 `lastIndexOf("}")` 找截断点，中文描述里常有 `}`/`]`，必须扫字符串状态。
- 用例验证：截断在字符串里 / 截断在数组里 / 正常输出 / 带说明文字，四种都能解析。

  image-storage，其余走 media）+ 等上传落地再 importProject，最后 pushProjectToCloud。
  顺序必须是「先传素材 → 再导入 → 再推文档」，否则 serializeDoc 拿不到 object_key。
